# LumaShift — Chrome 智能深色模式插件需求

## 1. 产品目标

开发一个 Chrome 浏览器插件 LumaShift，将原本没有良好深色适配的亮色网页自动转换为深色主题。

核心目标不是简单反色，而是让转换后的页面自然、舒适、清晰，接近网站原生深色主题的效果，同时保持较好的兼容性和较低的资源开销。

产品优先级：

视觉质量 ≈ 兼容性 ≈ 性能 > 功能数量。

最终目标是：用户可以长期保持插件开启，并且大多数时候感觉不到插件的存在。

---

## 2. 第一版范围

第一版面向桌面版 Chrome，采用 Manifest V3，主要支持普通 HTTP / HTTPS 网页。

必须包含：

- 自动将普通亮色网页转换为深色主题；
- 全局开启 / 关闭转换；
- 网站级转换设置及持久保存；
- 调整全局主要背景色和文字色；
- 一键恢复默认配色；
- 设置立即生效，无需刷新页面；
- 正确处理动态内容和常见页面交互；
- 简洁的 Popup 界面，展示当前状态及必要控制项。

以下能力不作为第一版必须交付的内容：

- 跟随系统主题、按时间自动切换；
- 网站独立配色、网站级高级规则编辑；
- 大量高级颜色参数和主题预设；
- 账号、云同步及其他远端服务；
- 其他浏览器适配；
- 本地文件和无痕模式支持。

不因增加高级功能而影响核心转换质量、兼容性和性能。

## 3. 深色主题显示效果

### 3.1 背景与视觉层级

页面主体和常见 UI 区域应合理转换为深色，包括背景、卡片、导航栏、侧边栏、表格、输入框、下拉菜单、弹窗、Tooltip 和代码块等。

不同区域应保留必要的层次、边界和区分度，不应全部变成同一种黑色。

对于透明背景、嵌套背景和局部混合明暗区域，应结合实际呈现效果处理，避免只修改文字或背景一侧，造成不可读。

### 3.2 文字与语义颜色

正文默认使用柔和的浅色，不默认使用纯白色 `#FFFFFF`。

应合理区分正文、标题、次要文字、Placeholder、Disabled 状态、链接和强调文字，避免出现深底深字、浅底浅字等明显可读性问题。

尽量保留品牌色和具有语义的颜色，例如：

- 链接与强调色；
- 错误、警告、成功状态；
- 代码语法高亮与代码差异；
- 图表中用于区分类别或数据的颜色。

允许为适应深色背景调整颜色明暗，但不应将这些颜色全部覆盖为普通文字色。

### 3.3 其他视觉元素与媒体

合理处理边框、阴影、SVG、图标、CSS 图形、选区，以及 Hover / Active / Focus / Disabled 等状态。

照片、视频、截图等内容型媒体原则上保持原样，不应发生明显反色、失真或色彩异常。媒体内容本身的白色或亮色，不直接视为转换缺陷。

图标、Logo、背景图和 SVG 应根据用途谨慎处理，不能一律反色。无法可靠判断时，优先保持内容正常和页面可用。

### 3.4 自定义配色

用户设置的主要背景色和文字色作为全局主题基准，插件应协调不同层级的背景、文字和边框，而不是将所有元素简单替换为两种颜色。

默认配色应兼顾舒适度和可读性。用户选择明显低对比度的配色时，应提供提示和恢复默认入口，不强制覆盖用户选择。

“恢复默认配色”只重置颜色，不清空网站级设置。

## 4. 用户控制与状态规则

### 4.1 全局开关

全局开关是总开关：

- 关闭时，所有允许插件运行的页面停止转换，网站级设置仍然保留；
- 开启时，各页面按网站级设置执行；
- 初始默认开启，在取得必要的网站访问权限后自动生效。

### 4.2 网站级设置

网站级设置以当前标签页顶层页面的完整主机名为单位保存，不区分页面路径，不默认合并不同子域名。

例如，`www.example.com` 与 `docs.example.com` 分别设置。

支持以下三种状态：

| 状态 | 行为 |
|---|---|
| 自动，默认状态 | 普通亮色页面自动转换；页面当前已经是深色时，尽量跳过 |
| 强制转换 | 忽略自动跳过判断，应用插件深色主题 |
| 保持原样 | 不进行转换 |

规则优先级：

页面访问限制 / 授权状态 → 全局开关 → 网站级设置。

“自动”判断关注页面当前是否已经呈现深色，而不是仅因为网站提供深色模式选项就跳过。

自动识别不要求对所有网站完全准确，但必须允许用户通过网站级设置覆盖误判，且不应因判断不稳定而频繁切换主题。

### 4.3 设置生效与持久化

全局开关、网站级设置和配色应在浏览器重启后保留。

修改全局开关或配色后，已经打开且允许插件运行的相关页面应及时更新；修改网站级设置后，该网站已经打开的相关标签页也应更新。

网站设置可以切回“自动”，撤销用户对该网站的强制指定。

### 4.4 Popup 界面

Popup 保持简洁，优先展示：

- 全局开关；
- 当前网站的转换设置；
- 当前页面的实际状态；
- 主要背景色、文字色和恢复默认配色入口。

实际状态应能区分：正在转换、全局已关闭、网站保持原样、检测到页面已为深色、页面不支持或未获授权等情况。

不得只显示“已开启”，却不解释当前页面为什么没有转换。

## 5. 主题恢复、兼容性与页面生命周期

### 5.1 恢复原主题

统一使用“原主题 / 插件深色主题”的概念，而不是假设原主题一定是亮色。

关闭转换时，应撤销插件造成的视觉修改，恢复网站当前本应呈现的样式，而不是强制改成亮色，也不能简单恢复为开启插件时的旧快照。

不得覆盖网站在插件启用期间自行发生的正常样式和主题变化。

切换主题不得：

- 刷新页面；
- 丢失输入内容、焦点、滚动位置等交互状态；
- 中断媒体播放或破坏页面功能；
- 因反复切换产生样式叠加、重复处理或资源持续增长。

关闭转换后，应停止不必要的转换计算，仅保留响应后续设置变化所需的最低开销。

### 5.2 常见页面与动态内容

尽可能支持普通 HTML、SPA、无限滚动、动态弹窗、动态组件，以及常见复杂 Web UI。

正确处理：

- 页面刷新、跳转和新标签页；
- SPA 路由切换；
- 内容新增、删除及已有元素的样式变化；
- 动态加载的菜单、弹窗和其他组件；
- 网站自身在亮色和深色主题间切换；
- 用户实时切换插件设置。

不得破坏页面布局、点击、输入、滚动、动画及原有交互逻辑。

### 5.3 特殊场景边界

在方案和测试结果中明确 iframe、Shadow DOM 等场景的支持程度及限制，不笼统承诺全部支持。

Canvas / WebGL 第一版以保持内容正常、交互可用为目标，不要求对其内部内容重新着色。

`chrome://` 等浏览器内部页面、Chrome 扩展商店等受限制页面，应在 Popup 中明确提示不支持。

浏览器内置 PDF 阅读器不作为第一版支持范围。

暂不支持或无法访问的局部内容应尽量保持原样，不得因此影响整个页面。

## 6. 性能与降级原则

性能与视觉质量同等重要，不能为了更完整的颜色转换无限增加计算和内存开销。

核心要求：

- 页面打开后尽快应用深色主题，尽量减少明显闪白；
- 原主题与插件深色主题之间切换快速，无明显卡顿；
- 页面静止后，不持续产生明显的额外 CPU 占用；
- 大型 DOM、无限滚动和频繁更新的 SPA 不应因插件明显变慢；
- 不应明显影响滚动、输入、动画和其他交互；
- 多标签页及后台标签页的累计开销应受到控制；
- 长时间运行和反复切换后，插件引入的资源占用不应无界增长。

不得通过长时间隐藏页面、阻塞内容展示或禁止交互来掩盖闪白。

出现视觉完整性与页面可用性冲突时，优先保证主要内容可读、关键交互正常和页面流畅，允许局部保留原样，不应导致整个页面不可用。

### 6.1 性能预算与测量

在原型阶段固定测试设备、Chrome 版本、测试页面和操作流程，建立基线，并给出明确的 MVP 性能预算。

预算应包含具体指标和测量方法，不能只使用“快”“低”“基本流畅”等描述，也不能到交付时才根据结果倒推目标。

至少测量：

| 维度 | 测量内容 |
|---|---|
| 首次生效 | 首屏开始变暗和基本稳定的时间，以及可见闪白情况 |
| 主题切换 | 从用户操作到可见区域完成切换的时间 |
| CPU | 页面空闲及动态更新期间的额外开销 |
| 内存 | 扩展自身和受影响标签页的增量，而不只看扩展后台 |
| 动态页面 | 大量内容更新、持续滚动和路由切换时的性能变化 |
| 长时间运行 | 反复操作后的资源趋势及停止操作后的稳定情况 |
| 多标签页 | 前台、后台页面同时存在时的累计开销 |

测试应在相同条件下对比插件禁用、安装但关闭转换、启用转换三种状态，并说明统计口径和重复测量方式。

## 7. 隐私与权限

遵循最少必要权限原则，而不是单纯追求权限数量最少。

允许申请实现普通网站自动转换所必需的访问权限，但必须说明每项权限的用途，不申请与核心功能无关的权限。

要求：

- 页面分析和主题生成在浏览器本地完成；
- 用户设置默认在本地保存；
- 不向第三方上传网页内容、浏览记录或用户配置；
- 第一版不引入账号、遥测、广告或云端推理；
- 核心转换功能不依赖额外远端服务。

“智能”不意味着必须接入大模型或其他在线分析服务。

## 8. 技术方案原则与实现流程

本需求不预设具体深色转换方案。

不要因为实现简单就默认采用 CSS Filter、整页反色或某一种固定技术路线，也不要求为了自研而从零实现所有能力。

正式实现核心引擎前，应完成：

1. 调研有代表性的成熟插件和开源实现，分析主要技术路线；
2. 比较视觉质量、兼容性、CPU、内存、首次转换和动态页面处理等方面的取舍；
3. 用小规模原型验证关键风险，并建立初步性能基线；
4. 形成简短的方案说明，明确选型、支持边界、降级方式和性能预算，再推进完整 MVP。

可以使用组合方案，但应由实际验证结果支撑，不以长篇调研代替可运行验证。

允许参考和合理复用成熟开源组件，但必须说明来源、许可证、复用范围及其性能和维护影响。不得仅更换名称和界面，将现有产品包装为已经满足本需求的实现。

优先建设通用转换能力。针对个别网站的补充适配可以存在，但不应主要依赖逐站硬编码，也不要求第一版提供高级规则编辑界面。

## 9. 测试与验收

### 9.1 测试集

建立可持续使用的回归测试集，包含真实网站和可控测试页面。

真实网站覆盖：

搜索、新闻 / 内容、Wiki、社区、视频、开发者网站、文档、Dashboard、密集表格、复杂表单、SPA 和无限滚动。

可从 GitHub、Wikipedia、Google / Baidu 搜索、知乎、Bilibili、Reddit、Hacker News 和典型文档站中选择具有代表性的页面，不要求为凑数量而扩大范围。

每项测试应明确具体页面、初始主题和操作步骤，例如：

打开文章 → 展开评论 → 加载更多 → 打开菜单 → 切换主题。

可控测试页面用于稳定复现：

动态增删内容、已有元素变色、嵌套透明背景、混合明暗区域、各种交互状态、大量节点更新、媒体展示和反复切换等边界场景。

### 9.2 验收内容

视觉方面：主要内容可读、界面背景合理、层级清楚、语义颜色可区分、媒体不失真，菜单、弹窗和交互状态正常。

功能方面：布局和交互正常，动态内容及 SPA 路由切换正常，主题切换不刷新页面、不丢状态，关闭后能够干净恢复。

状态方面：全局与网站规则优先级正确，设置能够持久化并同步到相关标签页，原生深色识别及手动覆盖正常，不支持页面有明确提示。

性能方面：按照第 6 节的固定环境、流程和预算提供实测结果，不以主观感受或单次测量替代验证。

具有原生深色模式的网站，应分别验证其原生亮色、原生深色及主题切换过程，避免只验证插件自动跳过后的状态。

### 9.3 问题分级与结果真实性

在已声明支持并纳入验收的场景中，以下属于阻断问题：

- 主要内容不可读；
- 关键交互失效；
- 媒体明显失真；
- 严重或持续卡顿；
- 关闭后无法正常恢复；
- 插件引入的资源占用持续异常增长。

个别装饰元素不够美观、非关键局部适配不完整，可以作为已知问题记录，但不能影响主要使用流程。

未测试、无法访问或需要登录才能验证的场景，必须明确标注，不得记为通过。可控页面的替代验证不得被描述为对应真实网站已经通过。

后续修改核心转换逻辑时，应重新运行相关回归测试。

## 10. 交付要求与完成定义

交付内容至少包括：

- 完整源码；
- 可通过 Chrome“加载已解压的扩展程序”安装的构建产物；
- 构建、安装和基本使用说明；
- 简短的技术方案、关键取舍和支持边界说明；
- 可复现的测试页面、操作流程及必要测试脚本；
- 实际视觉与性能测试结果、已知问题和未验证项目；
- 第三方依赖及必要的许可证说明。

第一阶段完成标准：

安装插件并授予必要权限 → 打开普通亮色网站 → 自动获得自然的深色主题 → 主要内容、媒体、交互和动态内容正常 → 能快速切换并恢复原主题 → 能按网站控制 → 配色与状态能够保存 → 性能达到预先确定的验收预算。

不能仅以“网页能够变黑”或“代码已经写完”作为完成标准。

第一阶段优先交付一个可长期使用、问题和限制透明的 MVP，而不是功能很多但效果不稳定、资源开销过大的插件。
